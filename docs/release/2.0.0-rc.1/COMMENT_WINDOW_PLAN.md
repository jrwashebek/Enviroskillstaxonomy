# EMST 2.0.0-rc.1: comment-window plan

- **Prepared by:** CA (an AI agent role, not a person), WP-16, 2026-10-23. Plan only: it opens nothing. The project lead decides when external comment opens.
- **Basis:** `docs/governance/CONTRIBUTING.md` §4 and §6; `docs/governance/GOVERNANCE_CHARTER.md` 6.3; ADR-0009 §4; ADR-0031 §10; `docs/methods/WP15_SIGNOFF.md`.
- **What is under comment:** the released records and views of `2.0.0-rc.1`. Their counts are in `RELEASE_NOTES.md` and `counts.json` in this folder. Both are generated by the build, so this plan repeats no numbers.

- **Why 60 days.** 2.0.0 is a MAJOR release, and the charter sets 60 days of candidate comment for a major or structural change (charter 6.3; CONTRIBUTING §4). The window is not shortened.
- **Planning dates.** These are illustrations, not commitments. If every condition held by early January 2027, a window opening 2027-01-04 would close 2027-03-05. Adjudication would then be due by 2027-04-04, 30 days after close. The NGO pilot's research round 1 (April–May 2027) would then use a release that has had public comment. If the conditions slip, the window slips. Nothing in rc.1 is described as final in the meantime.

## 2. How to comment

- **Channel.** Comments go through the project's GitHub Issues page, as the explorer's "Challenge a judgment" page explains. Give the record ID, the release ID (`2.0.0-rc.1`) and what should change. The explorer itself collects nothing.
- **Open item for AS and CP:** a route for people without a GitHub account, or whose agency policy bars GitHub. Until one exists, stage A partners can send comments through their pilot coordinator, who files them without personal details.
- **No personal data.** Comments must not name or describe identifiable people. An issue that does is edited to remove the details or closed, and the reason is recorded (ADR-0012).

## 3. What is open, and what is not

**Comment especially welcome on:**
1. **Tasks and indicators of the P1 roles.** Do they describe the work as practitioners do it?
2. **Venue values and instrument links.** Which legal or policy instrument requires, permits or removes a competency in each sector (`views/venue_applicability.json`)?
3. **The competency targets added by rule.** These are target levels set mechanically from the role level (`docs/build/WP-16/generated/role_target_additions.csv`; ADR-0031 §5 item 3).
4. **Crosswalk rows (X2–X12).** All are agent-drafted candidates.
5. **Scope.** What is deferred to rc.2 and what is withheld until re-verified (both are counted in the release notes). Comment on scope, since the withheld records are not published.
6. **The display rules.** What views show and hide before any human study (display gate 1.1.0; use tiers).

**Not open for comment:**
- **Tribal-related content.** It is held. Requests about it are logged and held until a Tribal Advisory Council exists and decides (CONTRIBUTING §6; ADR-0007 §D).
- **Agent ratings and tags as findings.** They are AI agents' drafts (`raterType: llm`). Comments that agree with them are recorded but are not agreement among subject-matter experts. Only a recorded study can change a value's display status.

## 4. Adjudication

- **Triage** within 30 days of receipt. Each comment gets a type (E, C, S, D, X or T), an owner and a priority.
- **Disposition** for every comment within 30 days after the window closes: Noted, Accepted, Accepted with modification, Deferred or Rejected, each with a reason (charter 6.3).
  - The owning agent code drafts the disposition.
  - A named human editor decides and merges: bots and agents open pull requests, and only humans merge (CONTRIBUTING §4). At rc.1 the project lead acts as the interim Editorial Board (Q8 default, `PROJECT_LEAD_DECISIONS.md`).
- **Disposition log** at `docs/release/2.0.0-rc.1/comment_dispositions.csv`, created when stage B opens. Columns: `issue`, `record_id`, `type`, `owner`, `disposition`, `reason`, `decided_by`, `decided_on`, `change_record`. Counts by type and disposition are generated from it at close; none are typed.
- **Where changes go.** E and C changes may go to the next rc as a PATCH after editor review. S, D and X changes go to the next candidate. Every merged change gets a change record with its `semverImpact` (SPEC §12.5).

## 5. Facts that move during the window

The register's re-check dates still apply during the window (`docs/methods/claims_register.csv`, column `recheck_by`; `WP15_SIGNOFF.md` §3).
- A fact that changes is corrected through an E change, outside the comment cycle.
- A record whose claim becomes unverified is withheld from the next build (`data/v2/governance/release_withheld.yaml`; ADR-0031 §8).
